# pax-orchestrate 契约缺口与决策清单

静态分析产出，不调 API。基线：`skills/pax-orchestrate/SKILL.md` W1–W4（8026 字符，
与 `evals/results/internal_routing_results.json` 的 `meta.contract_chars` 一致）。

分析对象是**内部路由的 W2 风险评分四个 1–3 量纲** + W1 二级意图边界。
这些维度是契约里唯一需要主观判断的地方，也是实测中唯一出现能力下降的地方
（`risk_score` 75.0%、`risk_level` 80.0%，GATE 未达标项全部集中在此）。
查表/MECE/链式拼接类检查项（primary_intent、route、cross_repo 等）两次运行都 ≥95%，
不在排查范围内。

判定标准：一个缺口成立，当且仅当**同一段题面可以自洽地推出两个不同的分数**，
且两边都能引用契约原文。纯措辞问题（模型没读懂我的话）不算缺口。

## 一、契约缺口清单

### 已被模型实测暴露（3 个）

#### G1. impact_scope：「内部工具」与「多用户」重叠 ✅ 已补（2026-10-03）

- **场景**：内部工具但有多人使用（内部运营后台、内部管理平台、内部报表系统）
- **判 1 依据**：判据原文「单模块、单用户、无外部依赖」，示例明确列「内部工具」
- **判 2 依据**：判据原文「多模块、多用户、有内部依赖」，示例明确列「多用户影响」
- **冲突点**：「内部工具」没有限定用户数。内部工具 + 多人使用，1 和 2 的判据都命中
- **已暴露**：`pax-risk-medium-03` 3/3 全错。模型判 1，gold 写 2，模型 reasoning 原文：
  「不涉及……列表页 1 个模块、不跨团队」。契约 impact_scope=1 的示例里列了「内部工具」，模型照读
- **建议补法**：给「内部工具」加限定——「内部工具（仅本人使用）」算 1；
  「内部工具但有多个使用人」按「多用户」算 2。判据改为「单模块、**单使用人**、无外部依赖」

#### G2. irreversibility：「可轻易回滚」与「前端部署可回退」重叠 ✅ 已补（2026-10-03，采用方案 a）

- **场景**：前端改动，上线后可一键切回旧版
- **判 1 依据**：判据「可轻易回滚，无需外部协调」，示例列「代码修改」
- **判 2 依据**：示例明确列「前端部署（可回退）」
- **冲突点**：区别只在「轻易」vs「需要步骤」，但「一键切回」到底算哪种没定义。
  「代码修改」和「前端部署」在示例里覆盖了同一个场景
- **已暴露**：`pax-risk-medium-03` 3/3 全错（同一条题，与 G1 同时暴露）
- **建议补法**：二选一——
  - (a) 「已部署的改动即使可回退也至少算 2」，把 1 限定为「未部署的本地修改」
  - (b) 「可一键回滚且无需数据迁移的算 1」，把 2 限定为「需要数据修复或人工步骤」
  推荐 (a)，与「生产部署无回滚计划 = 3」形成清晰梯度

#### G3. uncertainty：「有先例可循」与「需要验证假设」重叠 ✅ 已补并收窄（2026-10-03 12:24）

- **初版补法**：加边界「方案已知但需要验证一轮再上线的算 2，不算 1 的「有先例可循」」
- **初版实测（第一轮，54 次调用）**：`pax-risk-high-02` 的 uncertainty 从 v1.6 的 3/3
  掉到 1/3（模型 2/3 判 2，gold 1）。该题 prompt 是「标准的数据清理流程，公司有明确的
  清理脚本和操作手册」——按初版字面读，「需要验证一轮」覆盖了所有生产操作，把本该
  算 1 的「有明确手册」也拉成了 2
- **收窄依据**：区分点是「验证是否探索未知」，不是「是否需要验证」。high-02 有明确脚本
  和手册（验证方式已知，照做即可）；medium-02 要跑测试验证调用顺序（验证一个假设）。
  两者的 gold 分别是 1 和 2
- **收窄后补法**：「需要验证**一个未验证的假设**（调用顺序、性能、边界行为等）再上线的
  算 2；照既有脚本/手册执行、验证方式已知的算 1 的「有先例可循」」
- **收窄后实测（54 次调用）**：high-02 uncertainty 回到 3/3，全 13 项检查 100%，GATE PASS

### 静态分析发现（6 个，2026-10-03 已补/已回滚）

#### G4. coordination_cost：「单人可完成」与 2 档判据的优先级 ✅ 已补（2026-10-03 12:24）

- **原分析（部分有误）**：我以为 low-02 的 gold cco=1（实际是 2），据此推断「code review
  不能作为 1/2 的区分依据」，并把它从 2 的示例移除
- **事实**：low-02 prompt 明确写「需要走一次 code review」且 gold cco=2；medium-01 同样
  「需要 code review」且 gold=2；medium-03/high-02 写「不需要其他人配合」且 gold=1。
  **原始契约的「需要 code review」作为 2 的依据完全自洽**——我误读了 gold
- **后果**：第一次重跑（含此补法）coordination_cost 掉到 76.2%（low-02 3/3 全错，
  模型正确遵循新契约判 1，gold 写 2）；已回滚 coordination_cost 的示例改动，第二次重跑
  恢复到 85.7% PASS
- **但 medium-03 暴露了真实缺口**：prompt 写「运营模块的 3 个文件」且「由我一个人完成，
  不需要其他人配合」，gold cco=1。按契约 2 的判据「跨文件修改」判 2，但「不需要他人
  配合」应优先于文件数——**优先级未定义**
- **补法**：「『跨文件修改』指多文件联动的实质重构（前后端联动、跨模块接口改造），
  不是字面的『改动了 ≥2 个文件』。prompt 明确写『单人完成／不需要其他人配合』的，
  以『单人可完成』为准判 1，不因改动文件数升 2」
- **自洽性验证**：与 7 条 risk gold 全部自洽——low-02（2 文件 + code review，未说单人）=2、
  medium-01（后端接口+前端按钮 + code review）=2、medium-02（3 服务联动 + code review）=2、
  high-01（多文件 + 表结构定义，未说单人）=2、high-02（单人执行，不需配合）=1、
  medium-03（3 文件 + 明确不需配合）=1、low-01（咨询类）=1
- **实测（54 次调用）**：medium-03 coordination_cost 从 1/3 回到 3/3，coordination_cost
  全项 100%，GATE PASS。本轮无新 FAIL 出现

- **后果**：与 `pax-risk-high-01` 的 gold cco=2 冲突。该题 prompt 明确写

  多文件 = 1」，模型判 1（2/3），gold 写 2。这与 G4 的回滚联动：模块定义的前提

### D1. 【外部】用户明确说出 skill 名/同义词时，该不该直选 L1 skill？✅ 已决：B（2026-10-03）

- **问题**：`pax-pos-09`「帮我 review 这个 PR，看看有没有安全漏洞或潜在的 bug」
- **gold 现状**：`["pax-orchestrate"]`

- **两条 gold 都有支撑**：
  - 选 `pax-review` 的理由：用户明确说「review」，skill 目录里 `pax-review` 就是干这个的
  - 选 orchestrator 的理由：orchestrator 的设计意图是所有任务统一入口，
    review 只是其中一个下游动作，可能还需要 diagnose/rollback 配合
- **A 选项：允许直选**。用户说「review」就选 `pax-review`，说「诊断」就选 `pax-diagnose`
  - 对 gold 的影响：`pax-pos-09` → `["pax-review"]`，`pax-pos-10` → `["pax-diagnose"]`
  - 连带影响：对照组 8 次 missing_entry 里至少 6 次的归因要翻转为「正确」
  - 连带影响：18 个 skill 的 description 里「不要直接选择」这类禁令可能可以删除
- **B 选项：不允许，必须走 orchestrator**。所有任务统一入口，由 orchestrator 分发
  - 对 gold 的影响：gold 不变
  - 连带影响：18 个 L1 skill 的 description 禁令是**必要的**，
    对照组 66.7% 的准确率损失是真实代价（不是 bug）
- **不定的后果**：`pax-pos-09`/`pax-pos-10` 两条 gold 定不了形；
  外部路由的 100% 和 71.1% 都不能单独当发布判断（这两个数字的差异完全取决于此决策）

## 附：静态排查方法说明

对四个维度各列出 1/2/3 的判据 + 示例，然后逐个组合相邻档次的判据，
找「同一个场景能同时命中两个档次的判据/示例」的位置。
判据原文来自 `SKILL.md` 第 137–191 行（W2），二级意图边界来自第 68–84 行（W1）。

判定缺口成立的门槛：两边都要能**引用契约原文**，不能只靠「我觉得应该算 X」。
这样筛下来，纯措辞问题被排除在外（那些是我出题的缺陷，不是契约的缺陷）。

`pax-risk-medium-03` 是最典型的例子：模型 reasoning 明确引用了契约 impact_scope=1 的
「内部工具」示例，我的 gold 明确引用了 impact_scope=2 的「多用户」判据，两边都对。
这种情况下改题面或改 gold 都不对——**是契约本身没定义清楚**。
