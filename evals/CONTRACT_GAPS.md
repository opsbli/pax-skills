# pax-orchestrate 契约缺口与决策清单

静态分析产出，不调 API。基线：`skills/pax-orchestrate/SKILL.md` W1–W4（8026 字符，
与 `evals/results/internal_routing_results.json` 的 `meta.contract_chars` 一致）。

分析对象是**内部路由的 W2 风险评分四个 1–3 量纲** + W1 二级意图边界。
这些维度是契约里唯一需要主观判断的地方，也是实测中唯一出现能力下降的地方
（`risk_score` 75.0%、`risk_level` 80.0%，GATE 未达标项全部集中在此）。
查表/MECE/链式拼接类检查项（primary_intent、route、cross_repo 等）两次运行都 ≥95%，
不在排查范围内。

判定标准：一个缺口成立，当且仅当**同一段题面可以自洽地推出两个不同的分数**，
且两边都能引用契约原文。纯措辞问题（模型没读懂我的话）不算缺口。

## 一、契约缺口清单

### 已被模型实测暴露（3 个）

#### G1. impact_scope：「内部工具」与「多用户」重叠 ★

- **场景**：内部工具但有多人使用（内部运营后台、内部管理平台、内部报表系统）
- **判 1 依据**：判据原文「单模块、单用户、无外部依赖」，示例明确列「内部工具」
- **判 2 依据**：判据原文「多模块、多用户、有内部依赖」，示例明确列「多用户影响」
- **冲突点**：「内部工具」没有限定用户数。内部工具 + 多人使用，1 和 2 的判据都命中
- **已暴露**：`pax-risk-medium-03` 3/3 全错。模型判 1，gold 写 2，模型 reasoning 原文：
  「不涉及……列表页 1 个模块、不跨团队」。契约 impact_scope=1 的示例里列了「内部工具」，模型照读
- **建议补法**：给「内部工具」加限定——「内部工具（仅本人使用）」算 1；
  「内部工具但有多个使用人」按「多用户」算 2。判据改为「单模块、**单使用人**、无外部依赖」

#### G2. irreversibility：「可轻易回滚」与「前端部署可回退」重叠 ★

- **场景**：前端改动，上线后可一键切回旧版
- **判 1 依据**：判据「可轻易回滚，无需外部协调」，示例列「代码修改」
- **判 2 依据**：示例明确列「前端部署（可回退）」
- **冲突点**：区别只在「轻易」vs「需要步骤」，但「一键切回」到底算哪种没定义。
  「代码修改」和「前端部署」在示例里覆盖了同一个场景
- **已暴露**：`pax-risk-medium-03` 3/3 全错（同一条题，与 G1 同时暴露）
- **建议补法**：二选一——
  - (a) 「已部署的改动即使可回退也至少算 2」，把 1 限定为「未部署的本地修改」
  - (b) 「可一键回滚且无需数据迁移的算 1」，把 2 限定为「需要数据修复或人工步骤」
  推荐 (a)，与「生产部署无回滚计划 = 3」形成清晰梯度

#### G3. uncertainty：「有先例可循」与「需要验证假设」重叠

- **场景**：中风险变更，方案已知但有先例，需要验证一轮再上线
- **判 1 依据**：判据「风险可控」，示例「有先例可循」
- **判 2 依据**：示例「需要验证假设」
- **冲突点**：「验证一下」本身意味着有风险，但「有先例」意味着风险可控。
  契约 1 的「风险可控」和 2 的「需要验证假设」在「先例 + 验证」场景上重叠
- **已暴露**：`pax-risk-medium-02` r0（3 次里 1 次偏差，模型判 1，gold 写 2）。
  这条题面是「调用顺序需要在测试环境验证一轮再上线」
- **建议补法**：明确「需要验证但方案已知 = 2」。
  或反过来：「有先例 = 1，不管是否需要验证」——但后者会让「高度不确定」和「有先例」
  的边界变模糊，不推荐

### 静态分析发现，尚未实测（6 个）

#### G4. coordination_cost：「单人可完成」与「需要 code review」

- **场景**：单人完成改动，但团队流程要求 code review
- **判 1 依据**：判据「单人可完成、无需协调」
- **判 2 依据**：示例明确列「需要 code review」
- **冲突点**：code review 是流程义务还是协调行为？如果所有改动都要 code review，
  那 code review 是 2 的充分条件，1 就不可能成立
- **为何未暴露**：我出题时都在 2 分场景写了「需要 code review」，
  在 1 分场景写了「不需要其他人配合」——我把歧义消化在题面里了
- **建议补法**：明确「code review 是流程义务，不构成分配协调；
  跨人协作才计 2」。或反过来，明确「需要 code review 即至少算 2」

#### G5. 判据的顿号语义（且 vs 或）

- **场景**：影响范围 3 的「系统级、跨团队、跨系统、全用户」；
  协调成本 2 的「需要模块内协调、跨文件修改」；影响范围 2 的「多模块、多用户、有内部依赖」
- **冲突点**：顿号并列到底是「满足任一」还是「同时满足」。
  **数据类基准明确写了「满足任一项」，但主判据没写**——同一个契约里两种写法
- **为何未暴露**：现有题面都只命中单一信号，没触发组合判定
- **建议补法**：主判据统一加「满足任一」，与数据类基准一致。
  这条改动小但影响面大——影响范围 3 如果读成「且」，判 3 的门槛会变得非常高

#### G6. irreversibility：「大规模数据迁移」无阈值

- **场景**：数据迁移
- **冲突点**：irreversibility 3 的示例写「大规模数据迁移」，但「大规模」没有阈值。
  对比 impact_scope 数据类基准有明确阈值（≥5 张表或 ≥1000 万行）。
  同一个契约里，影响范围有阈值、不可逆性没有
- **建议补法**：直接引用 impact_scope 的阈值——「数据量 ≥1000 万行或跨 ≥5 张表的迁移算 3」

#### G7. 「主链路数据」列举不全

- **场景**：订单查询、库存、商品详情、消息推送算不算主链路
- **契约现状**：数据类基准写「覆盖主链路数据（登录、支付、账务、资产台账）」
- **冲突点**：列举是示例还是穷举？契约没说。
  我在 `pax-risk-medium-02` 里特意写了「所有客户下单前必经的查询入口」来绕过这个问题，
  用了「全用户」这个明确的 3 分信号
- **建议补法**：加「包括但不限于」，或改成「覆盖用户核心操作链路（登录、支付、账务、
  资产台账等，含下单/库存/商品详情）」

#### G8. 「模块」粒度未定义

- **场景**：3 个文件 vs 3 个服务 vs 3 个包，哪个算「多模块」
- **冲突点**：影响范围 2 写「多模块」，协调成本 2 写「跨文件修改」，
  协调成本 3 写「跨仓库操作」——但「模块」和「文件」的关系没定义
- **建议补法**：定义「模块 = 一个可独立部署或可独立回滚的单元」。
  这样「3 个文件的改动」在同一模块内算 1，跨 3 个可独立部署的服务算「多模块」= 2

#### G9. uncertainty：「需求明确」与「部分需求未明确」

- **场景**：方案清晰，只是实现细节需要确认一次
- **判 1 依据**：「需求明确、方案清晰」
- **判 2 依据**：「部分需求未明确」
- **冲突点**：确认「交互细节」算不算「需求未明确」？契约 1 说「有明确规格」，
  细节确认是否意味着规格不完整？
- **为何未暴露**：`pax-risk-medium-03` 里 uncertainty 模型判 2、gold 也是 2，
  这条没分歧——但我能自洽地推出 1（方案清晰，只差细节确认），所以是潜在缺口
- **建议补法**：明确「需要产品/需求方确认任何一项 = 至少 2」

### 已补契约，待业务方确认（1 个）

#### G10. data_integrity 是否覆盖字段值校验失败

- **场景**：表单提交，字段值未通过正则/格式/长度校验而报错
- **契约现状**：W1 二级意图里 `data_integrity` 触发条件写「数据不一致、数据丢失、字段错误」，
  `ux_error` 写「前端报错、交互异常、UI 缺陷」。两者都可能命中「页面报错」
- **已做的裁决**：我在 v1.1 判断「字段值校验失败归 data_integrity，不标 ux_error」，
  并把这条写进契约 W1 的「易混淆边界」段
- **可争议之处**：如果团队认为「校验失败是 UX 问题」（提示文案、交互引导），
  那应该归 ux_error，gold 也要改
- **状态**：契约已补，`pax-intent-df-01` / `pax-route-df-01` 的 gold 已按此裁决落地。
  **这是我的判断，不是契约原文**。如果业务方不认，两处 gold 要改回

## 二、决策清单（4 项，都阻塞 gold 定形）

### D1. 【外部】用户明确说出 skill 名/同义词时，该不该直选 L1 skill？

- **问题**：`pax-pos-09`「帮我 review 这个 PR，看看有没有安全漏洞或潜在的 bug」
- **gold 现状**：`["pax-orchestrate"]`
- **实测**：v2.0（带禁令）3/3 选 orchestrator；对照组（无禁令）3/3 选 `pax-review`
- **两条 gold 都有支撑**：
  - 选 `pax-review` 的理由：用户明确说「review」，skill 目录里 `pax-review` 就是干这个的
  - 选 orchestrator 的理由：orchestrator 的设计意图是所有任务统一入口，
    review 只是其中一个下游动作，可能还需要 diagnose/rollback 配合
- **A 选项：允许直选**。用户说「review」就选 `pax-review`，说「诊断」就选 `pax-diagnose`
  - 对 gold 的影响：`pax-pos-09` → `["pax-review"]`，`pax-pos-10` → `["pax-diagnose"]`
  - 连带影响：对照组 8 次 missing_entry 里至少 6 次的归因要翻转为「正确」
  - 连带影响：18 个 skill 的 description 里「不要直接选择」这类禁令可能可以删除
- **B 选项：不允许，必须走 orchestrator**。所有任务统一入口，由 orchestrator 分发
  - 对 gold 的影响：gold 不变
  - 连带影响：18 个 L1 skill 的 description 禁令是**必要的**，
    对照组 66.7% 的准确率损失是真实代价（不是 bug）
- **不定的后果**：`pax-pos-09`/`pax-pos-10` 两条 gold 定不了形；
  外部路由的 100% 和 71.1% 都不能单独当发布判断（这两个数字的差异完全取决于此决策）

### D2. 【外部】多目标/歧义请求是否允许一次选多个 skill？

- **问题**：`pax-multi-01`「帮我诊断一下这个告警漏发的原因，修好之后写一份故障复盘报告」
  这类请求天然包含 diagnose + fix + docs 多个动作
- **gold 现状**：`["pax-orchestrate"]`（单标签）
- **实测**：v2.0 3/3；对照组 2/3（一次答了 `pax-orchestrate+pax-diagnose+pax-docs`）
- **A 选项：允许多标签**。gold 写成 `["pax-orchestrate","pax-diagnose","pax-docs"]`
  - 对 gold 的影响：`pax-multi-01`/`pax-multi-02` 的 gold 要改成多标签
  - 连带影响：`multi_exact` 检查项从「结构性 n/a」变成有实际题目，
    之前 README 里写的「补了等于自废武功」这个理由就不成立了
  - 连带影响：对照组的多标签答案（如 `orchestrate+pax-diagnose`）从「过度选择」变成「正确」
- **B 选项：不允许，入口单选**。多目标请求选 orchestrator，由它在工作流内分发
  - 对 gold 的影响：gold 不变，`multi_exact` 保持结构性 n/a
  - 连带影响：`multi_exact` 检查项应直接从 suite 配置里移除，
    而不是留一个永远 NaN 的指标
- **不定的后果**：`multi_exact` 指标去留不定；
  外部数据集 30 题里 2 条 multi 题的 gold 定不了形

  - 对 gold 的影响：`pax-risk-medium-03` 的 gold 不变，**契约改完重跑才算数**

## 三、建议的决策顺序

1. **先定 D1**（外部 L1 直选）。它决定外部路由两个核心数字（100% / 71.1%）的解读方式，
   也决定 18 个 skill 的 description 禁令去留。不定它，外部评估的一切结论都是悬空的。
2. **再定 D4**（impact_scope 内部工具）。它直接决定 internal 当前 GATE FAIL 的唯一未达标类目
   （risk_scoring 75%）的归因，也决定 `pax-risk-medium-03` 这条锁定题是 FAIL 还是我写错了。
3. **D2、D3 可以并行定**，影响面小（D2 影响 2 条题 + 1 个指标去留；D3 影响 2 条题的 secondary）。

四项都定完，gold 才能定形，外部 100%/71.1% 与内部 88.5% 才能一起当发布判断。

## 附：静态排查方法说明

对四个维度各列出 1/2/3 的判据 + 示例，然后逐个组合相邻档次的判据，
找「同一个场景能同时命中两个档次的判据/示例」的位置。
判据原文来自 `SKILL.md` 第 137–191 行（W2），二级意图边界来自第 68–84 行（W1）。

判定缺口成立的门槛：两边都要能**引用契约原文**，不能只靠「我觉得应该算 X」。
这样筛下来，纯措辞问题被排除在外（那些是我出题的缺陷，不是契约的缺陷）。

`pax-risk-medium-03` 是最典型的例子：模型 reasoning 明确引用了契约 impact_scope=1 的
「内部工具」示例，我的 gold 明确引用了 impact_scope=2 的「多用户」判据，两边都对。
这种情况下改题面或改 gold 都不对——**是契约本身没定义清楚**。
